# JsonGlossary

Diccionario de datos: cada propiedad JSON usada en los requests/responses de `split.card.service` (ver `RequestSamples.md` para ejemplos completos por endpoint), en orden alfabético. Nombres en camelCase — así los serializa Minimal API por default.

| Campo | Tipo JSON | Nullable | Dónde aparece | Descripción |
|---|---|---|---|---|
| `alertType` | string (enum) | no | `CardAlertResponse` (dentro de `cardAlerts`) | `"CutoffSoon"` \| `"PaymentDueSoon"`. Cuál de las dos fechas de la tarjeta está próxima — el corte o el pago. Una misma tarjeta puede generar ambas alertas a la vez si las dos fechas caen dentro de la ventana. |
| `amount` | number | no | `RegisterTransactionRequest`, `TransactionResponse`, `PeriodTransactionResponse` | Monto **total original** de la compra, en la moneda indicada por `currency`. Para una compra en cuotas, esto NUNCA cambia — sigue siendo el total de la compra completa, no una cuota. Para saber cuánto corresponde pagar en un periodo específico, ver `periodAmount` (solo existe en `PeriodTransactionResponse`). |
| `bank` | string | no | `CreateCardRequest`, `CardResponse` | Nombre del banco emisor de la tarjeta (ej. `"BAC Credomatic"`). Texto libre, sin validación de catálogo. |
| `byCard` | array de `CardTotalResponse` | no | `HouseholdDashboardResponse` | Un elemento por cada tarjeta `Credit` del household (las `Debit` no aparecen — ver nota en `type`). Incluye tarjetas sin compras todavía en el periodo actual, con `totalCrc`/`totalUsd` en `0`. Los totales ya están resueltos por periodo (una compra en cuotas suma su cuota, no el total). |
| `byPerson` | array de `PersonTotalResponse` | no | `HouseholdDashboardResponse` | Un elemento por cada persona que aparece en el `split` de alguna transacción visible para quien consulta. Si sos Contributor/RestrictedViewer, solo aparecen las personas con las que compartís transacciones — no es la lista completa de miembros del household (esa es `GET .../members`). |
| `cardAlerts` | array de `CardAlertResponse` | no | `HouseholdAlertsResponse` | Un elemento por cada corte/pago próximo (dentro de 5 días) entre todas las tarjetas Credit del household. Array vacío (no `null`) si no hay nada próximo. |
| `cardId` | string | no | `RegisterTransactionRequest`, `TransactionResponse`, `PeriodTransactionResponse`, `CardTotalResponse`, `CardAlertResponse`, `InstallmentAlertResponse` | Id de la tarjeta (`Card.Id`). |
| `cardName` | string | no | `CardTotalResponse` (dentro de `byCard`), `CardAlertResponse`, `InstallmentAlertResponse` | Nombre de la tarjeta — mismo valor que `CardResponse.name`, resuelto server-side para no obligar al cliente a cruzarlo con `GET .../cards`. |
| `createdByUserId` | string | no | `TransactionResponse`, `PeriodTransactionResponse` | Id del usuario que registró la transacción (`ActingUserId` al momento de crearla, extraído del JWT). No es necesariamente uno de los `split[].personId` — alguien puede registrar una compra y asignársela 100% a otra persona. |
| `currency` | string (enum) | no | `RegisterTransactionRequest`, `TransactionResponse`, `PeriodTransactionResponse`, `InstallmentAlertResponse`, `InstallmentPlanRequestInput` (implícito, ver nota) | `"CRC"` \| `"USD"`. Moneda de la transacción. |
| `cutoffDay` | number | **sí**, si `type` es `"Debit"` | `CreateCardRequest`, `CardResponse` | Día del mes (1–31) en que corta el estado de cuenta. Obligatorio si `type` es `"Credit"`; debe ir `null` si es `"Debit"` — el backend rechaza la combinación contraria con 400. |
| `date` | string (`yyyy-MM-dd`) | no | `CardAlertResponse` | La fecha real del corte o pago que dispara la alerta (según `alertType`) — no confundir con el query param `date` de `/cards/{cardId}/transactions`, que es un valor de entrada elegido por el cliente; este es un valor calculado por el servidor. |
| `daysUntil` | number | no | `CardAlertResponse` | Días entre hoy y `date`, calculado en el servidor. `0` significa que es hoy. Nunca negativo (una alerta solo se genera para fechas futuras o de hoy). |
| `daysUntilPaymentDue` | number | no | `InstallmentAlertResponse` | Igual que `daysUntil` pero específico de `paymentDueDate` — redundante con el `CardAlertResponse` de tipo `"PaymentDueSoon"` de la misma tarjeta, incluido acá también para no obligar al cliente a cruzar ambos arrays. |
| `defaultSplit` | array de `PersonShare` | no | `CreateSplitRuleRequest`, `SplitRuleResponse` | Split por default que se sugiere cuando `descriptionPattern` matchea el comercio de una compra nueva. Mismo shape que `split` (ver abajo), misma regla de suma a 100. |
| `descriptionPattern` | string | no | `CreateSplitRuleRequest`, `SplitRuleResponse` | Texto contra el que se compara `merchant` (contains, case-insensitive) para sugerir `defaultSplit` automáticamente. Ej: `"Netflix"` matchea `"NETFLIX.COM"`. |
| `detail` | string | no | Respuestas de error (`GlobalExceptionHandler`) | Mensaje específico de la excepción — texto libre, no apto para mostrar tal cual al usuario final sin traducir/formatear. |
| `email` | string | no | `LoginRequest`, `InviteUserRequest`, `UserResponse` | Email del usuario. Único por instalación (`IUserRepository.GetByEmailAsync` lo valida al invitar/registrar). |
| `grandTotalCrc` / `grandTotalUsd` | number | no | `HouseholdDashboardResponse` | Suma de `byCard[].totalCrc`/`totalUsd` — el total consolidado del periodo actual, sin conversión entre monedas (ver nota de diseño en `RequestSamples.md`). |
| `householdId` | string | no | Casi todos los contratos con alcance de hogar | Id del `Household` al que pertenece el recurso. En los endpoints de escritura vas por body; en los de lectura por segmento de ruta (`/api/households/{householdId}/...`). |
| `householdName` | string | no | `RegisterHouseholdRequest` | Nombre visible del hogar (ej. `"Familia Rodríguez"`). Solo se define una vez, al bootstrap — no hay endpoint para renombrarlo todavía. |
| `id` | string | no | Todas las Response de una entidad individual | Id generado por el backend (`Guid.NewGuid().ToString("N")`, no `ObjectId` de Mongo). Nunca lo generás vos del lado cliente. |
| `installmentAlerts` | array de `InstallmentAlertResponse` | no | `HouseholdAlertsResponse` | Solo tiene entradas cuando alguna tarjeta disparó `"PaymentDueSoon"` en `cardAlerts` — qué compras en cuotas forman parte de ese pago próximo. Array vacío si no aplica. |
| `installmentAmount` | number | no (dentro de `installments`) | `InstallmentPlanRequestInput` | Monto de **cada** cuota individual, tal como lo mandás al crear la compra. Una vez creada la compra, este valor vive en el backend como `InstallmentPlan.InstallmentAmount` y se expone después vía `periodAmount` en `PeriodTransactionResponse`/`InstallmentAlertResponse` — no hay un endpoint que devuelva el `InstallmentPlan` crudo. |
| `installmentNumber` | number | **sí** en `PeriodTransactionResponse`, no en `InstallmentAlertResponse` | `PeriodTransactionResponse`, `InstallmentAlertResponse` | Qué cuota es esta, dentro del periodo consultado (`1`, `2`, `3`, ...). `null` en `PeriodTransactionResponse` si la compra no fue en cuotas; en `InstallmentAlertResponse` siempre viene con valor porque ese array solo contiene compras en cuotas. |
| `installmentPlanId` | string | **sí** | `TransactionResponse`, `PeriodTransactionResponse` | Id del `InstallmentPlan` creado, o `null` si la compra no fue en cuotas (`installments` venía `null` en el request). |
| `installments` | object \| null | **sí** | `RegisterTransactionRequest` | `null` = compra sin cuotas (pago único). Si no es `null`, debe traer `totalInstallments` + `installmentAmount`. **Solo válido en tarjetas `type: "Credit"`** — si `cardId` apunta a una tarjeta `"Debit"` y `installments` no es `null`, el backend rechaza con 400 (`ApplicationValidationException`, mensaje: "Debit card purchases cannot be paid in installments..."). Una compra de contado no se paga en cuotas. |
| `merchant` | string | no | `RegisterTransactionRequest`, `TransactionResponse`, `PeriodTransactionResponse`, `InstallmentAlertResponse`; también query param en `/split-rules/suggest` | Nombre del comercio donde se hizo la compra, tal como aparece en el estado de cuenta. Es el campo contra el que matchea `descriptionPattern`. |
| `name` | string | no | `InviteUserRequest`, `UserResponse`, `CreateCardRequest`, `CardResponse` | Nombre visible — de la persona (`User.Name`) o de la tarjeta (`Card.Name`), según el contrato. |
| `ownerEmail` | string | no | `RegisterHouseholdRequest` | Email del primer Owner del hogar, creado atómicamente junto con el Household. |
| `ownerName` | string | no | `RegisterHouseholdRequest` | Nombre del primer Owner del hogar. |
| `ownerPassword` | string | no | `RegisterHouseholdRequest` | Password en texto plano — **solo en tránsito**, el backend lo hashea (PBKDF2) antes de guardarlo. Nunca se devuelve en ninguna response. |
| `ownerUserId` | string | no | `RegisterHouseholdResponse`, `CardResponse` | En `RegisterHouseholdResponse`: id del Owner recién creado. En `CardResponse`: id del usuario que registró la tarjeta (siempre un Owner, por la regla de autorización de `CreateCardCommandHandler`) — el nombre es un poco engañoso, no implica "dueño personal de la tarjeta física", es quien la administra en el sistema. |
| `password` | string | no | `LoginRequest`, `InviteUserRequest` | Password en texto plano, solo en tránsito (ver `ownerPassword`). |
| `paymentDueDate` | string (`yyyy-MM-dd`) | no | `InstallmentAlertResponse` | La fecha de pago calculada para el periodo actual de esa tarjeta — mismo valor que `date` en la entrada `"PaymentDueSoon"` de `cardAlerts` para esa misma tarjeta. |
| `paymentDueDay` | number | **sí**, si `type` es `"Debit"` | `CreateCardRequest`, `CardResponse` | Día del mes en que vence el pago del estado de cuenta (1–31, configuración de la tarjeta). No confundir con `paymentDueDate`, que es una fecha calculada concreta. Misma regla de nullability que `cutoffDay`. |
| `percentage` | number | no | `PersonShareRequest`/`PersonShareResponse`, dentro de `split`/`defaultSplit` | Porcentaje (0 exclusivo–100 inclusivo) que le corresponde a `personId` de ese monto. La suma de todos los `percentage` dentro de un mismo array `split` debe dar exactamente `100`, o falla con 400. |
| `periodAmount` | number | no | `PeriodTransactionResponse`, `InstallmentAlertResponse` | **Lo que corresponde pagar en el periodo consultado** — igual a `amount` para una compra sin cuotas, igual al monto de la cuota (`installmentAmount` original) para una compra en cuotas. Cualquier suma/total de "cuánto se debe este periodo" tiene que usar este campo, nunca `amount`. |
| `personId` | string | no | `PersonShareRequest`/`PersonShareResponse`, `PersonTotalResponse` | Id del `User` al que se le asigna ese `percentage` del split, o al que corresponde ese total en el dashboard. No tiene que ser quien registró la transacción (`createdByUserId`). |
| `personName` | string | no | `PersonTotalResponse` (dentro de `byPerson`) | Nombre resuelto server-side a partir de `personId` — el dashboard nunca devuelve solo el id crudo. |
| `purchaseDate` | string (`yyyy-MM-dd`) | no | `RegisterTransactionRequest`, `TransactionResponse`, `PeriodTransactionResponse`; también query param `date` en `/cards/{cardId}/transactions` | Fecha en que se hizo la compra **originalmente** — no cambia entre periodos, ni siquiera para una compra en cuotas que sigue apareciendo en periodos posteriores. El backend la usa para calcular a qué `StatementPeriod` pertenece la PRIMERA cuota (solo en tarjetas Credit). |
| `role` | string (enum) | no | `InviteUserRequest`, `UserResponse` | `"Owner"` \| `"Contributor"` \| `"RestrictedViewer"`. En `InviteUserRequest` el backend rechaza `"Owner"` con 400 (`ApplicationValidationException`) — un segundo Owner no se puede crear por esta vía. |
| `split` | array de `PersonShare` | no | `RegisterTransactionRequest`, `TransactionResponse`, `PeriodTransactionResponse` | Cómo se reparte `amount` (o `periodAmount`, según el contrato) entre los miembros del hogar. Ver `percentage`/`personId`. Mínimo 1 elemento, sin `personId` duplicados. |
| `status` | number | no | Respuestas de error | Código HTTP numérico, redundante con el status code real de la respuesta — está en el body también para que el cliente no dependa de leer headers. |
| `title` | string | no | Respuestas de error | Categoría corta del error (`"Forbidden"`, `"Resource not found"`, etc.) — ver tabla de excepciones en `RequestSamples.md`. |
| `token` | string | no | `LoginResponse` | JWT firmado (HS256). Se manda como `Authorization: Bearer {token}` en cada request subsiguiente que requiera auth. Expira según `JWT_EXPIRATION_MINUTES` (default 7 días). |
| `totalCrc` / `totalUsd` | number | no | `PersonTotalResponse`, `CardTotalResponse` | Suma de montos en esa moneda para esa persona/tarjeta, dentro del periodo actual — ya resuelto por periodo (cuotas incluidas correctamente). `0` es un valor real y esperado (tarjeta sin compras todavía), no un indicador de error. |
| `totalInstallments` | number | **sí** en `PeriodTransactionResponse`, no en `InstallmentPlanRequestInput`/`InstallmentAlertResponse` | `InstallmentPlanRequestInput` (al crear la compra), `PeriodTransactionResponse` (al consultarla), `InstallmentAlertResponse` | Cantidad total de cuotas de la compra (ej. `6` para "6 cuotas"). `null` en `PeriodTransactionResponse` si la compra no fue en cuotas — usar junto con `installmentNumber` para mostrar "Cuota X de Y". |
| `transactionId` | string | no | `InstallmentAlertResponse` | Id de la `Transaction` (misma entidad, mismo id que aparecería como `id` en `PeriodTransactionResponse`) — se llama distinto acá porque el objeto contenedor ya usa `id` implícitamente para otra cosa a nivel conceptual (la alerta en sí no tiene id propio persistido). |
| `type` | string (enum) | no | `CreateCardRequest`, `CardResponse` | `"Credit"` \| `"Debit"`. Determina si la tarjeta maneja `StatementPeriod`/cortes, si acepta `installments`, y si aparece en `GET .../dashboard`/`GET .../alerts` (solo `Credit` — una tarjeta Debit no representa deuda pendiente ni tiene corte/pago). |
| `userId` | string | no | `LoginResponse` | Id del usuario autenticado — mismo valor que devolvería `GET /api/auth/me` en su campo `id`. |

## Notas generales

- Los campos marcados **Nullable: sí** son los únicos que podés/debés mandar como `null` explícito en el JSON — omitir el campo por completo no es equivalente en todos los casos (depende del binding de Minimal API, pero mandar `null` explícito es siempre seguro).
- Ningún contrato de request incluye `actingUserId` — esa identidad sale del JWT (`Authorization: Bearer`), nunca del body. Si ves un ejemplo viejo (de antes de Auth) con ese campo, está desactualizado.
- Ningún contrato de response incluye `passwordHash` — verificado explícitamente en `UserContracts.cs` (`FromDomain` no lo mapea).
- `GET .../dashboard` es el único endpoint donde un mismo concepto ("nombre") aparece bajo dos claves distintas según el contexto (`cardName` vs. `personName`) en lugar de reusar `name` — a propósito, para que un cliente no tenga que inspeccionar la forma del objeto para saber a qué corresponde cada total.
- **`TransactionResponse` vs. `PeriodTransactionResponse`** son contratos distintos, no el mismo objeto con más campos: `GET /api/households/{householdId}/transactions` y `POST /api/transactions` devuelven `TransactionResponse` (solo `amount`, el total). `GET /api/cards/{cardId}/transactions?date=...` devuelve `PeriodTransactionResponse` (`amount` + `periodAmount` + info de cuota). No asumas que un cliente puede tratarlos como el mismo shape.
- `GET .../alerts` es puramente informativo/in-app — no hay push notifications todavía (ver `claude.md`, sección Alerts, para qué falta si se quiere agregar push real).
